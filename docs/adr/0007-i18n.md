- Issue #24 ➔ PR #27

## Decision

User-facing language is resolved via Spring's **`SessionLocaleResolver`**
(default locale `Locale.US`, i.e. `en`), switched via a **`?lang=` request
parameter** through `LocaleChangeInterceptor`, and rendered through Thymeleaf
`#{key}` expressions backed by **per-module message basenames**
(`i18n/admin`, `i18n/client`, `i18n/subscribers`, `i18n/identity`,
`i18n/catalog`, `i18n/ledger`, `i18n/subscriptions`, `i18n/common`) rather than
a single flat `messages.properties`. Five locales are supported: `ru`, `uk`,
`de`, `en`, `fr`. A missing key for any non-default locale falls back to the
default locale's translation rather than rendering a raw key.

## Context

The billing platform's admin and client Thymeleaf apps had no i18n support —
all UI text was hardcoded in English directly in templates. The primary user
base (subscribers, tech lead, and current admin operators) is predominantly
Russian- and Ukrainian-speaking, with German and French markets in scope, so
language support needed to cover all five locales across both apps sharing
one Spring context and one `PostgreSQL` database.

Four decisions had genuine alternatives and needed to be made explicitly
rather than defaulting to whatever Spring Boot ships with out of the box:

1. How is the selected locale **persisted** across requests — per-session,
   or longer-lived (cookie, account-level setting)?
2. How does the user **switch** language — query parameter, `Accept-Language`
   header negotiation, or locale segment in the URL path?
3. Are translation keys stored in **one file per locale**, or **split by
   module** to match the existing package structure
   (`identity`, `subscribers`, `catalog`, `subscriptions`, `ledger`,
   `web/admin`, `web/client`)?
4. What is the **default/fallback locale** when a key is missing or no
   locale has been selected yet — `en` or `ru`?

Decision criteria:
- Locale switching must work without requiring a page reload beyond a normal
  link/form navigation (no client-side JS framework in this SSR app).
- Translation files must stay maintainable as the app grows — a contributor
  adding one page should touch one file, not scroll a 500-key flat file.
- The default/fallback behavior must never surface a raw message key or throw
  to the user; it must degrade to *some* readable language.
- The mechanism must work identically for both the `admin` and `client` apps,
  which share one Spring context.

## Options

### Locale persistence
1. (SELECTED) `SessionLocaleResolver` — locale lives in the HTTP session only
2. `CookieLocaleResolver` — locale persisted in a browser cookie, survives session expiry
3. Locale stored on `ApplicationUser` entity, loaded at login

### Locale switching mechanism
1. (SELECTED) `?lang=` query parameter + `LocaleChangeInterceptor`
2. `Accept-Language` header negotiation (`AcceptHeaderLocaleResolver`)
3. Locale segment in URL path (`/ru/admin/...`)

### Message file organization
1. (SELECTED) Per-module basenames (`i18n/admin`, `i18n/client`, `i18n/subscribers`, ...)
2. Single flat `messages_*.properties` for the whole app

### Default/fallback locale
1. (SELECTED) `en` (`Locale.US`)
2. `ru`

## Consequences

### Locale persistence

#### Option 1 (SELECTED): SessionLocaleResolver
| Pro                                                                                     | Con                                                                                                               |
|-----------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| Zero extra infrastructure — no cookie handling, no schema change                        | Locale is lost on session expiry, logout, or new browser session — user re-selects language every time            |
| No PII/preference data leaves the server session; nothing to manage for cookie consent  | Two tabs in different sessions (e.g. incognito) can't share a selection, which is rarely desired anyway but noted |
| Matches the app's existing session-based auth model (`JSESSIONID`), no new moving parts |                                                                                                                   |

#### Option 2: CookieLocaleResolver
| Pro                                                                    | Con                                                                                          |
|------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| Survives session expiry, browser restarts, and logout                  | Adds a cookie to manage (name, max-age, path) and a cookie-consent surface to consider       |
| Better UX for infrequent visitors who don't want to re-pick every time | Slightly more config than a bean default; needs explicit `setCookieMaxAge` / `setCookieName` |

#### Option 3: Locale on ApplicationUser entity
| Pro                                                      | Con                                                                                                     |
|----------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| Persists indefinitely, follows the user across devices   | Requires a schema migration and a resolver that loads the user before rendering any page                |
| Single source of truth for a logged-in user's preference | Doesn't help unauthenticated pages (login page itself needs a language switcher before any user exists) |

### Locale switching mechanism

#### Option 1 (SELECTED): `?lang=` param + LocaleChangeInterceptor
| Pro                                                                                   | Con                                                                                      |
|---------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| Built into Spring MVC, one interceptor bean, no custom resolver logic needed          | URL is polluted with `?lang=xx` unless stripped after the switch; bookmarks may carry it |
| Works identically for GET links and forms; no JS required for a pure-SSR app          | Every switch is a full page reload (acceptable here — no SPA behavior in this app)       |
| Explicit user action always wins over any header/browser guess — predictable behavior |                                                                                          |

#### Option 2: Accept-Language header negotiation
| Pro                                                            | Con                                                                                                |
|----------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| Zero UI needed — works automatically based on browser settings | No explicit in-app switcher without extra work; user can't override the header choice easily       |
| Good first-visit default for unauthenticated pages             | Browser/OS language often doesn't match a user's actual preference (e.g. shared/library computers) |

#### Option 3: Locale segment in URL path
| Pro                                                            | Con                                                                                                          |
|----------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| Locale is visible and shareable/bookmarkable in the URL itself | Requires rewriting every `th:href`/`@{...}` route and the security/CSRF config to account for the prefix     |
| SEO-friendly if this were a public marketing site (it isn't)   | Biggest implementation cost of the three options for no benefit in a session-authenticated admin/billing app |

### Message file organization

#### Option 1 (SELECTED): Per-module basenames
| Pro                                                                                        | Con                                                                                                                                                                        |
|--------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Mirrors the existing package split (`identity`, `subscribers`, `catalog`, `ledger`, ...)   | A contributor must know/guess which module a new page's keys belong to (already caused rework once — `userProfile` moved from `admin` to `subscribers` mid-implementation) |
| Smaller, focused files — easier to review a diff for one feature                           | Cross-module key reuse requires either duplicating a key or picking one module as the "owner" and cross-referencing it                                                     |
| Matches `spring.messages.basename` already configured as a comma-separated per-module list |                                                                                                                                                                            |

#### Option 2: Single flat messages_*.properties
| Pro                                                              | Con                                                                                                                           |
|------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| No ambiguity about which file a key lives in — there's only one  | File grows unbounded as the app grows; five files (`ru`/`uk`/`de`/`en`/`fr`) each become a wall of keys spanning every domain |
| Trivial to grep for a key                                        | Larger diffs on every change; harder to review "what changed for the ledger feature" in isolation                             |

### Default/fallback locale


#### Option 1 (SELECTED): en (Locale.US)
| Pro                                                                                                             | Con                                                                                                                                                            |
|-----------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Matches Spring Boot's out-of-the-box default — no surprises for new contributors                                | Doesn't reflect the actual primary user base (predominantly ru/uk-speaking), so the "safe fallback" a user sees on a missing key is not their working language |
| `en` translations are the easiest for any contributor to write/review before native speakers translate the rest |                                                                                                                                                                |

#### Option 2: ru
| Pro                                                                                                                    | Con                                                                                                                                           |
|------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|
| Matches the actual majority user base — a missing key degrades to a language most users read                           | Diverges from Spring's implicit default; must be set explicitly everywhere (`Locale.of("ru")`) and kept consistent across every resolver bean |
| Reduces the practical impact of incomplete `uk` translations, since `ru`/`uk` are mutually intelligible for most users | English-speaking contributors reviewing PRs see Russian text on any missing key, which is harder to sanity-check without translation help     |

*Currently `en`, carried over from the Spring Boot default rather than a
deliberate choice for this user base — flagged as an open question in the
companion feature doc rather than re-decided here, since changing it is a
one-line config change with no schema impact.*
